# Информационная система бронирования мест в коворкинге

Учебный прототип на **Go + PostgreSQL**, фронтенд — обычный веб-сайт, оформленный под мобильный интерфейс **Telegram Mini App** (карточки, крупные кнопки, нижняя навигация). Запускается через `docker compose`.

## Стек

- Backend: Go 1.22 (стандартная библиотека `net/http`, `html/template`)
- База данных: PostgreSQL 16
- Запуск: Docker + docker-compose
- Авторизация: email + пароль (без обязательной авторизации через Telegram)

## Запуск

```bash
docker compose up --build
```

После запуска:

- Приложение: http://localhost:8080
- PostgreSQL: `localhost:5432`, БД `coworking`, пользователь `coworking`, пароль `coworking`

Остановить и удалить тома:

```bash
docker compose down -v
```

### Если Docker Hub недоступен (TLS handshake timeout)

По умолчанию базовые образы (`golang:1.22-alpine`, `alpine:3.20`, `postgres:16-alpine`) тянутся через `mirror.gcr.io` — пул-через-кэш Docker Hub от Google, обычно доступен из РФ без VPN. Если и он не открывается, переопредели реестр через переменную окружения:

PowerShell:
```powershell
$env:DOCKER_REGISTRY = "huecker.io"
docker compose up -d --build
```

Bash:
```bash
DOCKER_REGISTRY=huecker.io docker compose up -d --build
```

Известные доступные из РФ зеркала Docker Hub:

- `mirror.gcr.io` (по умолчанию)
- `huecker.io`
- `dockerhub.timeweb.cloud`

Если зеркало не использует префикс `library/` для образов из Docker Hub Library, дополнительно задай `DOCKER_REGISTRY_LIBRARY_PREFIX=""`.

## Реализованные функции

- **Регистрация / вход / выход.** Email + пароль, bcrypt-хеши, серверная валидация, cookie-сессии с HMAC-SHA256, ролевой доступ (`USER`, `ADMIN`).
- **Просмотр схемы коворкинга.** Карточный 3×3-grid с координатами `position_x/position_y`, статусы «свободно / занято / недоступно», обновление по выбору даты и интервала.
- **Создание бронирования (UC-3).** 9-точечная серверная валидация (авторизация, дата/время, прошлое, существование места, доступность, конфликты с другими и со своими бронями, лимит активных бронирований).
- **Мои бронирования + отмена (UC-4).** Фильтры по статусу и периоду, отмена своей активной брони с проверкой принадлежности, статус становится `CANCELLED_BY_USER`.
- **Админ-панель (UC-5/6/7).** CRUD по местам, фильтр + отмена/смена статуса бронирований, изменение лимита активных бронирований и `cancellation_lead_time_hours`.
- **Отчёты (UC-8).** Период, агрегаты по статусам, топ-5 популярных мест, загрузка по дням (с инлайн-баром), активность пользователей. Сохранение JSON-снимка в `reports`.

## Финальный сценарий проверки (полный пробой)

```bash
docker compose down -v
docker compose up --build
```

1. Открыть http://localhost:8080 — мобильный макет.
2. Зарегистрировать нового пользователя → редирект на главную → `/scheme`.
3. На `/scheme` выбрать дату завтра, интервал `10:00–12:00`, выбрать `A1`, нажать «Забронировать» → редирект на `/bookings`, видна запись со статусом «Активно».
4. Открыть `/bookings` → нажать «Отменить» → подтвердить → бронь становится «Отменено пользователем». На `/scheme` `A1` снова свободен.
5. Войти как `admin@example.com / admin` → `/admin`.
6. В разделе «Места» добавить место `D1`, отредактировать координаты, отключить, удалить.
7. В разделе «Бронирования» применить фильтр по email пользователя, отменить бронь админом → статус «Отменено администратором».
8. В разделе «Настройки» изменить лимит на `5`, сохранить.
9. Перейти на `/admin/report`, выбрать период за последние 30 дней, нажать «Построить» → видны таблицы и инлайн-диаграмма.
10. Под обычным пользователем попытаться открыть `/admin` → `403`.

## Этап 2 — что сделано

- БД PostgreSQL автоматически инициализируется скриптами `db/init/01_schema.sql` (схема) и `db/init/02_seed.sql` (начальные данные) через `/docker-entrypoint-initdb.d/`.
- Созданы все 6 сущностей из `.md`-файла: `users`, `workspaces`, `bookings`, `booking_settings`, `reports`, `notifications`.
- Созданы enum-типы: `role`, `workspace_type`, `booking_status`, `notification_type`.
- Внешние ключи: `bookings.user_id` → `users`, `bookings.workspace_id` → `workspaces`, `notifications.user_id` → `users`, `notifications.booking_id` → `bookings`, `reports.created_by` → `users`, `booking_settings.updated_by` → `users`.
- Ограничения: уникальный `email` пользователя, уникальное `name` места, `bookings.end_time > start_time`, `max_active_bookings_per_user > 0`, singleton-индекс на `booking_settings`.
- Начальные данные: администратор `admin@example.com` / `admin` (хеш bcrypt через `pgcrypto.crypt(... 'bf')`), 9 рабочих мест на сетке 3×3, настройки с лимитом 3 активных бронирования.
- Go-приложение подключается к PostgreSQL (драйвер `lib/pq`) и на странице `/scheme` загружает места из БД.

## Этап 3 — что сделано

- Регистрация по `full_name + email + password + password_confirm`. Все поля валидируются на сервере (обязательность, формат email, минимальная длина пароля 4, совпадение паролей, уникальность email). Пароль хранится только в виде bcrypt-хеша через `golang.org/x/crypto/bcrypt`.
- Вход по email и паролю. При успешном входе создаётся cookie-сессия. Cookie-токен подписан HMAC-SHA256, а сама сессия (token → user_id) хранится в памяти приложения.
- Logout (`/logout`) — удаляет сессию и сбрасывает cookie.
- Middleware: `withUser` (грузит пользователя из сессии), `requireUser`, `requireAdmin`.
- Защищены: `/scheme`, `/bookings` — для авторизованных пользователей; `/admin` — только для роли `ADMIN`.
- Админ при входе сразу попадает в `/admin`, обычный пользователь — в `/bookings`.
- В шаблонах формы показывают понятные ошибки, заголовок страницы и нижняя навигация автоматически обновляются после входа.

### Ручная проверка этапа 3

1. `docker compose up --build`.
2. Открыть `http://localhost:8080/login`, войти как `admin@example.com` / `admin` → редирект на `/admin`, в нижней навигации появилась вкладка «Админ».
3. Открыть `/logout`, затем `/register` — создать нового пользователя, например `test@example.com` / `test123`. Проверить редирект на `/bookings` и появление пользователя в БД.
4. Под обычным пользователем зайти на `/admin` → ответ `403 Доступ запрещён`.
5. Без cookie зайти на `/bookings` или `/admin` → редирект на `/login`.
6. Попробовать ошибки: неверный пароль, повторная регистрация на тот же email, несовпадающие пароли, некорректный формат email — на форме появляются понятные сообщения.

### Известные ограничения этапа 3

- Сессии хранятся в памяти процесса — после перезапуска контейнера приходится логиниться заново.
- Список «Мои бронирования» по-прежнему мокается — реальный список появится на этапе 6.

## Этап 4 — что сделано

- Страница `/scheme` принимает параметры `date`, `start`, `end` и обновляет занятость в реальном времени.
- Места из таблицы `workspaces` отображаются в виде сетки по `position_x` / `position_y`.
- Для каждого места определяется статус: `Свободно` (зелёный), `Занято` (красный, есть пересекающееся `CONFIRMED`-бронирование), `Недоступно` (серый, `is_available = FALSE`).
- Занятые и недоступные места не кликабельны (рендерятся как `<div>`), свободные — как ссылка с параметром `workspace_id`.
- При выборе места показывается карточка с номером, типом, зоной, выбранной датой и интервалом, статусом, и активной кнопкой «Забронировать» (форма уже отправляется на `/bookings/create`, обработка появится на этапе 5).
- Серверная валидация: некорректная дата или время → ошибка; время окончания не позже времени начала → ошибка; попытка выбрать занятое/недоступное место → сообщение и кнопка «Забронировать» отключается.
- Запрос занятости использует SQL: `SELECT DISTINCT workspace_id FROM bookings WHERE status = 'CONFIRMED' AND start_time < $end AND end_time > $start`.

### Ручная проверка этапа 4

1. Войти как `admin@example.com` / `admin` или зарегистрировать пользователя.
2. Открыть `/scheme`. По умолчанию выбраны сегодня 09:00–12:00 и все доступные места — зелёные, `B2` — серое.
3. Поменять дату/время → нажать «Показать занятость». Сетка перерисовывается.
4. Кликнуть на свободное место → появляется карточка «Выбранное место» с активной кнопкой.
5. Попытаться открыть ссылку с `workspace_id` отключённого места (например, B2) — кнопка «Забронировать» неактивна, выводится понятное сообщение.
6. Установить время окончания меньше или равное началу — выводится ошибка «Время окончания должно быть позже времени начала».
7. (Если хочется проверить статус «Занято»): добавить тестовое бронирование вручную:
   ```sql
   INSERT INTO bookings(user_id, workspace_id, start_time, end_time, status)
   SELECT u.user_id, w.workspace_id, '2026-05-07 10:00:00+03', '2026-05-07 12:00:00+03', 'CONFIRMED'
     FROM users u, workspaces w
    WHERE u.email='admin@example.com' AND w.name='A1';
   ```
   Затем открыть `/scheme?date=2026-05-07&start=11:00&end=13:00` — A1 будет красным.

### Известные ограничения этапа 4

- Кнопка «Забронировать» отправляет форму на `/bookings/create`, но сам обработчик появится на этапе 5.
- Список «Мои бронирования» и админ-панель пока работают на моковых данных бронирований.

## Этап 5 — что сделано

- `POST /bookings/create` создаёт `bookings`-запись со статусом `CONFIRMED`.
- Полный набор проверок (UC-3 из `.md`) выполняется в строгом порядке:
  1. Пользователь авторизован.
  2. Дата и время выбраны и валидны.
  3. `end > start`.
  4. Интервал не в прошлом (`end > NOW()`).
  5. Место существует.
  6. Место доступно (`is_available = TRUE`).
  7. На это место нет другого `CONFIRMED`-бронирования с пересекающимся интервалом.
  8. У пользователя количество активных бронирований не достигло лимита `booking_settings.max_active_bookings_per_user`.
  9. У пользователя нет другого `CONFIRMED`-бронирования с пересекающимся интервалом.
- При успехе — редирект на `/bookings?flash=created`, на странице видно сообщение «Бронирование создано».
- При ошибке — редирект на `/scheme` с сохранением выбранной даты/времени/места и текстом ошибки в `?error=...`.
- Страница `/bookings` теперь показывает реальные записи пользователя (объединённые с `workspaces` для имени, типа, зоны), статусы переведены на русский, для будущих `CONFIRMED`-броней показывается кнопка «Отменить» (логика отмены — этап 6).
- Админская страница `/admin` тоже теперь читает реальные `bookings` и значение лимита из `booking_settings`.

### Ручная проверка этапа 5 (UC-3)

1. Войти, открыть `/scheme`.
2. Выбрать свободное место (например, A1) на завтра 10:00–12:00 → нажать «Забронировать».
3. Открыть `/scheme?date=<завтра>&start=11:00&end=13:00` — A1 теперь красный.
4. Попробовать создать конфликтующую бронь — на `/scheme` появляется ошибка «Это место уже занято на выбранный интервал».
5. Поставить дату в прошлом → ошибка «Нельзя бронировать в прошлом».
6. Попробовать `B2` (отключённое) → ошибка «Место отключено администратором».
7. Создать 3 брони — на 4-ю система отвечает «Превышен лимит активных бронирований (3)».
8. Зарегистрировать второго пользователя в другом браузере → попытаться забронировать тот же интервал на A1 → конфликт, бронирование отклонено.

### Известные ограничения этапа 5

- Кнопка «Отменить» уже видна, но обработчик `/bookings/cancel` появится на этапе 6.
- Админ-панель только показывает данные — управление местами и настройками будет на этапе 7.

## Этап 6 — что сделано

- `POST /bookings/cancel` отменяет бронь после набора проверок (UC-4):
  1. Авторизован.
  2. Бронь существует.
  3. Бронь принадлежит текущему пользователю (иначе `403`).
  4. Статус ровно `CONFIRMED`.
  5. `start_time > NOW()` (нельзя отменить уже стартовавшую бронь).
  При успехе — `status = CANCELLED_BY_USER`, `cancelled_at = NOW()`, редирект на `/bookings?flash=cancelled`.
- Перед отправкой формы — `confirm()`-диалог в браузере.
- На странице `/bookings` добавлены фильтры:
  - **Статус**: Все / Активные (`CONFIRMED`) / Завершённые (`COMPLETED`) / Отменённые (`CANCELLED_BY_USER` или `CANCELLED_BY_ADMIN`).
  - **Период**: Все / Будущие (`end_time > NOW()`) / Прошлые (`end_time <= NOW()`).
- После отмены `/scheme` сразу показывает место как свободное (потому что выборка по `status = 'CONFIRMED'`).

### Ручная проверка этапа 6 (UC-4)

1. Войти, создать бронь на завтра.
2. Открыть «Мои бронирования» → видна запись, бейдж «Активно», кнопка «Отменить».
3. Нажать «Отменить» → подтвердить → попадаем обратно с зелёным флэшем «Бронирование отменено, место снова доступно».
4. Открыть `/scheme` на тот же интервал — место снова зелёное.
5. Применить фильтр «Отменённые» → видна именно отменённая бронь с бейджем «Отменено пользователем».
6. Из аккаунта Bob создать бронь на A2; зайти под `admin@example.com` и попытаться отменить эту бронь POST-запросом с другим `booking_id` — получаем `403 Можно отменять только свои бронирования`.

### Известные ограничения этапа 6

- Админская отмена бронирований и управление местами/лимитами появятся в этапе 7.

## Этап 7 — что сделано

Реализованы UC-5, UC-6, UC-7 из `.md` (управление местами, бронированиями, настройками).

### Места (`POST /admin/workspaces/...`)
- `create` — добавление места: имя, тип (`DESK` / `MEETING_ROOM` / `LOUNGE`), зона, доступность, `position_x`, `position_y`.
- `update` — редактирование тех же полей.
- `toggle` — включение/отключение места без удаления (`is_available`).
- `delete` — удаление места **только при отсутствии будущих `CONFIRMED`-бронирований** (иначе понятная ошибка).

### Бронирования (`POST /admin/bookings/...`)
- На странице `/admin` список всех бронирований с фильтрами: даты `с/по`, email пользователя (substring `ILIKE`), статус, конкретное место.
- `cancel` — администратор может отменить любую активную бронь, статус становится `CANCELLED_BY_ADMIN`, `cancelled_at = NOW()`.
- `status` — изменение статуса с проверкой допустимых переходов:
  - `CONFIRMED → COMPLETED` (кнопка «Завершить»)
  - `CONFIRMED → CANCELLED_BY_ADMIN` (через тот же `cancel`).
  Любые другие переходы (например, оживить отменённую бронь) запрещены.

### Настройки (`POST /admin/settings`)
- Просмотр текущего значения `max_active_bookings_per_user`.
- Сохранение нового значения; проверка: положительное целое (`>0`).
- Сохранение `cancellation_lead_time_hours` (≥0); поле `updated_by` записывается как user_id текущего администратора.

### Ручная проверка этапа 7

1. Войти как `admin@example.com / admin`.
2. Раздел «Места»:
   - «+ Добавить место» → создать `D1`, тип `DESK`, зона «Лаунж», (2;2). Проверить, что появилось в списке.
   - Раскрыть карточку `D1` → изменить координаты на (3;3). Сохранить.
   - Снять галочку «Доступно» в карточке и сохранить → плитка серая, на `/scheme` пользователь видит «Недоступно».
   - Нажать «Удалить» → удалено.
3. Создать как пользователь бронь на `A1`. В админке нажать «Удалить» на `A1` → ошибка «Нельзя удалить место с активными будущими бронированиями».
4. В разделе «Бронирования» применить фильтр по email пользователя — видна только его запись. Нажать «Отменить» → статус становится «Отменено администратором».
5. В разделе «Настройки» поставить лимит `5`, `lead_hours=2` → сохраняется. Поставить `-1` → ошибка.
6. Под обычным пользователем POST на любой `/admin/...` маршрут → `403`.

### Известные ограничения этапа 7

- Раздел «Отчёты» появится на этапе 8.
- Переход `CONFIRMED → COMPLETED` доступен только администратору; автозавершение по времени не реализовано (это учебный прототип).

## Этап 8 — что сделано

Реализован UC-8 «Отчёты», обновлён README, проведена финальная проверка по всем сценариям.

- `GET /admin/report` — выбор периода `from..to` (по умолчанию: последние 30 дней).
- Серверная валидация дат (формат `YYYY-MM-DD`, `to >= from`); пустой отчёт показывает «За выбранный период бронирований нет».
- Агрегаты считаются на стороне БД одним запросом на каждый блок:
  - **Сводка**: всего бронирований, подтверждённых, завершённых, отменённых пользователем, отменённых администратором.
  - **Популярные места**: топ-5 мест по количеству бронирований.
  - **Загрузка по дням**: количество бронирований на каждый день периода + инлайн-«bar chart» из CSS (без сторонних JS-библиотек).
  - **Активность пользователей**: топ-10 пользователей по количеству бронирований за период.
- Кнопка «Сохранить отчёт» инсертит JSON-снимок в таблицу `reports` (поля `date_range_start`, `date_range_end`, `data jsonb`, `created_by`).

### Ручная проверка этапа 8

1. Войти как `admin@example.com / admin` → `/admin/report`.
2. Без бронирований — таблица показывает «За выбранный период бронирований нет».
3. Создать как пользователь несколько бронирований (часть отменить) → перезагрузить отчёт → видны корректные счётчики, топ-места, график.
4. Нажать «Сохранить отчёт» — флэш «Отчёт сохранён», в БД `SELECT * FROM reports;` появилась запись c JSON-данными.
5. Указать `from > to` — ошибка «Дата окончания должна быть не раньше даты начала».
6. Под обычным пользователем `GET /admin/report` → `403`.

### Архитектурные заметки и ограничения прототипа

- Конкурентность создания бронирований проверяется на уровне Go-валидации, а не через `SELECT … FOR UPDATE` — для учебного прототипа этого достаточно, но при высокой нагрузке возможна гонка двух одновременных POST-ов; в production-варианте сюда добавлялись бы транзакция и сериализация через `EXCLUDE USING GIST(workspace_id WITH =, tsrange(start_time, end_time, '[)') WITH &&)` или `serializable isolation`.
- Уведомления (`notifications`) и автоматическое завершение бронирований по времени не реализованы — это явно за пределами учебного прототипа.
- Все шаблоны — серверный рендер `html/template`, без сборки фронтенда. Это сознательное упрощение, чтобы код можно было читать и демонстрировать без тулчейна.
